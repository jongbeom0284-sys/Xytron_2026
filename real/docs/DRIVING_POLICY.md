# 주행 규칙

이 문서는 차가 **어디를 보고, 어디로 가려 하고, 얼마나 꺾는지**를 설명한다.
값 자체는 전부 `ros2_ws/src/kobot_lane_drive/config/twinmixing_center.yaml` 에 있고
그 파일에도 같은 설명이 주석으로 붙어 있다.

## 원칙

**노란 중앙선을 중심으로 2차선 전체 폭을 쓰며 달린다.**

한 차선 안에 갇혀 달리면 코너 반경이 차선 폭만큼 줄어든다. 이 차의 최소 회전반경은
약 1.0m 라 그만한 코너에서는 한 차선 안에 머무를 수 없다. 도로 전체 폭을 쓰면 같은
코너를 더 큰 반경으로 돈다.

예외는 하나다. **장애물 차량이 한 차선을 막았을 때만** 반대편 차선으로 비켜서고,
추월이 끝나면 다시 중앙으로 돌아온다.

---

## 1. 눈 — 무엇을 보고 있나

TwinMixing 신경망이 매 프레임 두 장의 마스크를 낸다.

| 마스크 | 뜻 | 화면 색 |
|---|---|---|
| `driving_mask` | 주행 가능 영역 | 파랑 / 주황(왼쪽 차선) / 보라(오른쪽 차선) |
| `lane_mask` | 차선 픽셀 (색 구분 없음) | 초록 |

`lane_mask` 는 **중앙선만이 아니라 양쪽 흰 차선도 잡는다.** 그래서 이것만으로는
중앙선을 못 고른다. 원본 프레임의 색을 따로 봐야 한다.

### 보는 범위 (ROI)

```
          y=240  ┌──────────────┐  위쪽은 벽·천장·조명이 섞여 목표선을 흔든다
                 │              │
                 │   사다리꼴    │  가로도 자른다. 중앙선은 늘 화면 중앙 부근이고
                 │              │  멀수록 좁은 범위로 모인다
          y=374  └──────────────┘  아래는 차 앞 라이다가 화면을 가린다
                    (라이다)
```

- **세로 y 240 ~ 374.** 아래 경계는 프레임 중앙값 영상으로 실측했다 —
  라이다가 y=375 부터 x 240~420 을 가린다.
- **가로는 사다리꼴.** 아래 반폭 307px, 위 반폭 192px. 직사각형으로 자르면 먼 행에서
  화면 끝까지 훑어 벽과 바닥을 후보로 끌어들인다.

## 2. 목표선 고르기 — 네 단계 우선순위

| 순위 | `path_source` | 무엇을 보나 |
|---|---|---|
| 1 | `YELLOW_LINE` | 색으로 확인된 노란 중앙선 |
| 1' | `YELLOW_LINE_GHOST` | 위가 끊긴 동안의 외삽 (실측 도로가 없을 때만) |
| 2 | `CENTER_GAP` | 두 주행영역 사이의 틈 |
| 3 | `REGION_CENTER` | 주행영역이 하나면 그 한가운데 |
| 4 | `HOLD` / `WAITING` | 마지막 유효값 유지 → 타임아웃 시 정지 |

**외삽본은 실측 도로보다 뒤다.** 예전에는 외삽 신뢰도가 임계 위에 있는 동안 실측
도로보다 먼저 채택돼, 도로가 멀쩡히 보이는데도 최대 1.3초까지 몇 프레임 전 잔상을
따라갔다.

### 1단계 — 노란 중앙선을 어떻게 찾나

**색을 절대값으로 자르지 않는다.** 실내에서 갈색(=어두운 주황)이 노랑과 색상축에서
겹친다. 실측에서 노란 점선의 밝기가 108, 나무 바닥이 127 로 **선이 오히려 더 어두웠다.**
절대 임계로는 원리적으로 못 가른다.

대신 **LAB 의 `b*`(파랑↔노랑) 채널에 가로 top-hat** 을 건다.

```
가로로 긴 커널로 opening  →  좁은 줄무늬가 지워짐
원본 - opening           →  좁은 줄무늬만 남음
```

넓고 균일한 누런 면(나무 바닥)은 opening 으로도 살아남아 차이가 0 이 된다.
조명이 바뀌거나 화이트밸런스가 장면 전체를 밀어도 **국소 차이는 유지된다.**

### 나무벽은 색이 아니라 거리로 거른다

벽의 나무 슬랫은 세로 줄무늬라 top-hat 이 찾는 "좁은 노란 줄"과 똑같이 생겼다.
실제로 목표선이 도로가 아니라 나무 기둥 위에 얹힌 주행이 있었다.

화이트밸런스를 고정한 뒤 표본 2691개 대 143개로 색을 다시 재도 갈리지 않았다.

| | 진짜 중앙선 | 나무벽 |
|---|---|---|
| LAB `b*` | 143 / 155 / 172 | 136 / 138 / 146 |
| 채도 | 107 / 192 / 232 | 94 / 106 / 129 |
| **도로까지 거리** | **4 ~ 18px** | **107px** |

*(10 / 50 / 90 퍼센타일)*

색은 꼬리가 겹친다. **거리는 6배 차이로 확실히 갈린다.**
→ 후보가 도로에서 **40px 이상 떨어지면 중앙선이 아니다.**

더 빡빡한 옛 조건(`require_road_anchor`, `require_road_on_both_sides`)은 코드에
남아 있지만 기본 꺼짐이다. 중앙선이 주행영역 가장자리 바로 바깥에 놓이는 프레임이
있어서, 켜면 진짜 중앙선까지 걷어낸다(한 프레임에서 23행 중 21행 탈락).

### 점선 대응

중앙선이 점선이라 행 사이가 빈다. 검출이 끊긴 동안 최근 lookahead x 의 추세를
연장한다(`YELLOW_LINE_GHOST`). 20프레임을 넘으면 포기하고 다음 순위로 내려간다.

### 프레임 사이 연속성

행 스캔의 **시작점을 직전 프레임에서 이어받는다.** 매번 화면 중앙에서 새로 시작하면,
곡선에서 중앙선이 중앙을 벗어났을 때 바닥 근처의 엉뚱한 노란 조각이 더 가깝다는
이유만으로 시작점이 되고 거기서부터 잘못 따라 올라간다. 실측에서 그 때문에 한
프레임의 목표가 +81 에서 −206px 으로 뒤집혔다.

### 3단계 — 얇은 틈 메우기

`REGION_CENTER` 는 한 줄에서 **가장 넓은 조각 하나**만 쓴다. 중앙선 자국이 도로를
두 조각으로 가르면 도로의 절반이 통째로 빠지고, 그 한가운데가 실제 중앙에서 크게
벗어난다(실측 369 대 267).

그래서 이 단계 **직전에만** 폭 22px 이하의 틈을 도로로 메운다. 센터 갭 판정이 이미
끝난 뒤라서 진짜로 갈라진 도로를 지울 위험이 없다.

## 3. 장애물 판정 — 네 조건이 모두 맞아야 한다

한 조건이라도 빠지면 차선을 넘지 않는다. 잘못 넘는 것이 안 넘는 것보다 훨씬 위험하다.

| # | 조건 | 근거 |
|---|---|---|
| ① | 그쪽 차선 폭이 반대편보다 뚜렷하게 좁다 | 카메라 |
| ② | 그 차선 **자신의 평상시 폭** 대비 뚜렷하게 줄었다 | 카메라 |
| ③ | 같은 쪽 옆 차선 코리도에 임계 거리 이내의 물체 | 라이다 |
| ④ | 지금 직선 구간이다 | 기하 |

②가 필요한 이유는 실측으로 확인했다. 어떤 구간은 좌 214px / 우 70px 로 오른쪽이
**상시** 좁다. 폭 비율만 보면 프레임의 54%가 점유로 읽힌다. 벽을 낀 구간은 원래
한쪽이 좁다 — **좁다는 사실이 아니라 좁아졌다는 변화**가 장애물의 신호다.

### 라이다 코리도

부채꼴이 아니라 **차량 좌표계의 직사각 상자**로 자른다.

```
              y (앞)
   2.50m ──────┼──────
        ┌──┐   │   ┌──┐     옆 차선 상자: 앞 0.35~2.5m, 옆 0.12~0.75m
        │좌│   │   │우│
   0.35m└──┘───┼───└──┘
               ●  차량
   ◄───────────┼───────────► x (왼쪽 +)
```

도로 밖의 벽은 옆으로 너무 멀고, 범퍼 옆 반사는 앞쪽 거리가 모자라 상자 밖이다.

**라이다는 차 앞으로 돌출 장착돼 후방 163도를 차체가 가린다.** 실측으로 정면 각도를
역산했다 — 가림 구간 원시 220.4~22.7도, 그 중심(후방) 301.6도 → 정면 원시 121.6도.
보정값 `-2.1217 rad`.

## 4. 주행 라인 상태기계

```
                 좌측 점유 확정
       ┌──────────────────────────► SHIFT_RIGHT ─┐
CENTER ┤                                          ├─ 통과 판정 ─► RETURNING ─► CENTER
       └──────────────────────────► SHIFT_LEFT  ─┘
                 우측 점유 확정
```

| 상태 | 목표 x | 속도 |
|---|---|---|
| `CENTER` | 중앙선 위 (2차선 중앙) | 100% |
| `SHIFT_LEFT` / `SHIFT_RIGHT` | 비어있는 차선의 중앙 | 75% |
| `RETURNING` | 중앙선 위 | 75% |

목표 x 는 항상 **레이트 리밋**(260 px/s)을 거친다. 급전환은 조향 포화를 부른다.

## 5. 조향

```
조향 = sign × ( kp × gain × 정규화오차  +  kd × 오차변화율 )

정규화오차 = (여유구간 25px 을 뺀 가로오차) / (화면폭/2)
```

**미분 항이 감쇠다.** 차가 중앙으로 다가오는 중이면 오차가 줄고 있어 미분이 음수가
되고 조향이 미리 풀린다. 중앙에 닿을 때 조향이 이미 0 에 가까워야 그대로 지나쳐
반대편으로 넘어가지 않는다.

**여유 구간 25px** 이 중앙 근처의 사냥을 없앤다. 없으면 오차 10px 에도 조향한다.
차선 반폭이 250px 이니 10% 다.

### 화면 속 차선 기울기는 제어에 쓰지 않는다

원근 때문에 **차가 선과 완전히 나란히 서 있어도** 선은 소실점으로 수렴해 기울기가
음수로 나온다. 가로오차와 반대로 작용한다. 실제로 그것 때문에 조향 부호가 뒤집힌
주행이 있었다 — 오차 +40px(목표 오른쪽)인데 legacy −25(왼쪽 조향).

기울기는 화면 표시와 진단용으로만 계산한다.

### 게인 이력

| 값 | 결과 |
|---|---|
| 4.0 | 오차 91px 만에 풀락. 심한 오버슈트 |
| 1.4 | 곡선에서 오차 102px 에 legacy 29 밖에 안 나감 |
| **3.2** | 여유 구간이 중앙 근처를 잘라 주므로 직선은 안 흔들리고 곡선은 돈다 |

## 6. 안전 경계

- 인식·판단 노드에는 **모터 publisher 가 없다.** `/xycar_motor` 를 발행하는 파일은
  `twinmixing_center_drive_bridge_node.py` 하나뿐이고 시험이 이를 강제한다.
- 브리지는 `armed:=true` 없이는 프로세스조차 생기지 않는다.
- 회피는 `maneuvers_enabled` 기본 거짓으로 잠겨 있다.
- 목표선을 잃으면 마지막 유효 명령을 유지하고, 0.30초 이상 끊기면 브리지가 0 을 보낸다.

## 7. 카메라 설정이 인식의 전제다

색으로 판단하는 이상 카메라 설정이 틀리면 그 아래 모든 게 틀어진다.

| 항목 | 값 | 왜 |
|---|---|---|
| `white_balance` | **2800K** | 이 방 조명 색온도가 낮다. 4600K 로 잠그면 화면 전체가 초록으로 뜨고 노란 마스크가 차체·노면으로 번진다 |
| `auto_white_balance` | 꺼짐 | 켜두면 프레임마다 색이 흔들려 색 판단의 기준선이 없어진다 |
| `exposure` | 40 | 자동 노출은 흰 바닥에 물려 화면이 날아간다 |
| `brightness` | 0 | 50 으로 올라가 있어 화면이 완전히 날아간 적이 있다 |

**2800K 는 추측이 아니라 실측이다.** 화이트밸런스 2800~6500K × 노출 20~100 의 전
조합을 찍고 각 조합에 노란 마스크를 겹쳐 눈으로 확인했다. 2800 에서만 마스크가
노란 점선 위에만 얹혔고, 4600 이상에서는 차체와 노면으로 번졌다.

`usb_cam` 은 이 값들을 ROS 파라미터로 읽기만 하고 **장치에는 쓰지 않는다.**
그래서 `sensors.launch.py` 가 노드 기동 8초 뒤 같은 값을 `v4l2-ctl` 로 한 번 더 건다.
값의 출처는 `kobot_vehicle/config/camera.yaml` 하나다.
