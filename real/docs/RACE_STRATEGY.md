# 2026 본선 주행 전략과 성능 계약

## 1. 최적화 목표

이 프로젝트의 목표는 최고 순간속도가 아니라 다음 최종 기록을 최소화하는 것이다.

```text
최종 기록 = 3바퀴 실제 주행시간 + 차선 이탈·충돌·미션 실패 추가시간
```

따라서 개발 우선순위는 `완주 가능성 → 무벌점 반복성 → 구간별 속도` 순서로 둔다.
한 번의 빠른 주행보다 같은 설정으로 3바퀴를 반복 완주하는 능력을 먼저 검증한다.

공개 규정은 미션을 수행한 총 주행시간과 미션별 벌점을 합산한다고 명시하지만,
세부 규정은 당일까지 변경될 수 있다. 신호 의미, 지름길 진입 조건, 벌점, 랩 판정
방식은 제공받은 최신 본선 세부 규정을 단일 설정 파일로 옮기고 경기 전 다시 확인한다.

## 2. 고정 트랙 활용 원칙

고정 트랙이라는 사실은 속도 계획과 미션 활성 구간에 사용하되, 조향을 시간표대로
재생하는 방식으로 사용하지 않는다. 타이어·배터리·노면 차이로 시간 기반 open-loop
조향은 쉽게 누적 오차를 만든다.

- 트랙을 직선, 완만한 곡선, 급곡선, 신호 접근, 지름길 분기, 합류, 결승 구간으로 나눈다.
- 구간마다 기본 목표속도와 미션 ROI를 갖는 `sector profile`을 사용한다.
- 현재 구간은 랩 수, VESC 속도 적분, IMU yaw, 차선 곡률 이력, 미션 표식을 함께 사용해 추정한다.
- 한 센서만으로 구간을 확정하지 않으며, 불일치하면 더 보수적인 구간 속도를 사용한다.
- 차선과 장애물은 매 프레임 닫힌고리로 확인한다. 고정 트랙 정보는 센서 판단을 덮어쓰지 않는다.

## 3. 런타임 구조

```text
camera 30 Hz ──> fast lane perception ──> metric path ──> lateral controller
      │                    │                    │
      └─> mission ROI ──> mission events      ├─> speed scheduler ──> command arbiter
lidar/imu/vesc ──> safety + sector estimator ─┘                         │
race supervisor FSM <────────────────────────────────────────────────────┘
```

모든 출력은 `race supervisor`와 `command arbiter`를 거친다. 차선 인식기나 신호등
인식기가 모터 토픽을 직접 발행하지 않는다.

### 3.1 주 차선 인식

첫 주력은 CPU에서 동작하는 고전 영상처리 파이프라인이다.

1. 카메라 왜곡 보정과 고정 ROI
2. LAB L 채널 정규화 또는 제한적인 CLAHE
3. 흰색·노란색 soft score와 밝기 gradient 결합
4. BEV에서 형태학 처리와 작은 연결요소 제거
5. RANSAC 또는 강건 다항식으로 좌우 외곽 경계 추정
6. 양쪽 흰색 외곽선의 중앙 경로 생성
7. 한쪽만 보이면 검증된 트랙 폭으로 복원
8. 노란 점선은 중심·방향의 보조 관측으로만 사용
9. 이전 프레임 예측과 현재 측정의 시간 필터링

고정 HSV/LAB 임계값 하나로 성공 여부를 결정하지 않는다. 색상, 경계, 폭, 평행성,
곡률 연속성, 이전 프레임 일치도를 합쳐 `lane_confidence`를 계산한다.

### 3.2 학습 기반 보조 인식

PIDNet-S 같은 경량 세그멘테이션은 고전 방식과 동일한 입력 영상을 받아 A/B 평가한다.
TensorRT FP16 최적화 후 지연·정확도 계약을 모두 통과할 때만 주력 또는 보조로 채택한다.
현재 평균 약 85.59 ms인 CLRerNet Python 추론 경로는 경기 주력의 지연 계약을 충족하지
못하므로 비교 기준과 데이터 선별 도구로 유지한다.

학습 기반 결과가 늦거나 신뢰도가 낮으면 최신 고전 인식 결과를 사용한다. 두 결과가 크게
다르면 속도를 낮추고 외곽 흰색 경계와 트랙 폭 제약을 우선한다.

### 3.3 신호등과 지름길

신호등 인식은 전 구간에서 무거운 검출기를 돌리지 않고 `SIGNAL_APPROACH` 구간에서
고정 또는 예측 ROI에만 활성화한다. 인식 결과가 한 프레임에서 바로 경로를 바꾸지 않는다.

- 후보 결과를 timestamp, class, confidence와 함께 이벤트로 발행한다.
- 초기 기준은 최근 5회 중 3회 이상 일치이며, 실제 영상으로 오탐률을 측정해 조정한다.
- 유효 구간, 판정 마감선, 최신성, 지름길 진입로 안전 조건을 모두 통과해야 결정을 latch한다.
- 판정이 불확실하거나 마감 시각을 넘기면 세부 규정상 유효한 기본 경로를 선택한다.
- 선택 후에는 합류 완료까지 프레임별 색상 변화로 결정을 뒤집지 않는다.

지름길은 단순히 인식 confidence가 높다는 이유로 선택하지 않는다. 예상 단축시간보다
오판·이탈·충돌의 기대 추가시간이 작고, 실제 반복시험에서 성공률이 확보됐을 때 사용한다.

### 3.4 상태기계

최소 상태는 다음과 같다.

```text
PRESTART
  -> NORMAL_LANE
  -> SIGNAL_APPROACH -> SIGNAL_CONFIRM
       -> MAIN_ROUTE | SHORTCUT_ROUTE
  -> MERGE
  -> LAP_COMPLETE -> NORMAL_LANE | FINISH

any state -> DEGRADED -> RECOVERY | SAFE_STOP
```

각 상태는 허용 속도, 사용할 ROI, 필요한 센서, 진입 조건, timeout, 실패 시 fallback을
명시한다. 랩이 바뀔 때 순간 인식 상태는 초기화하지만 카메라와 제어기 진단 통계는 유지한다.

## 4. 실시간 성능 계약

2026-08-14 Kobot 실측 기준 카메라는 `640x480 rgb8`, 약 30 Hz다. 경기 코드의 목표는
FPS 숫자가 아니라 최신 프레임으로 만든 명령의 나이를 제한하는 것이다.

| 항목 | 1차 통과 기준 |
|---|---:|
| 카메라 수신율 | 평균 28 Hz 이상 |
| 고전 차선 인식 | P95 20 ms 이하 |
| 경로 생성 + 제어 | P95 5 ms 이하 |
| 영상 timestamp → 명령 생성 | P95 50 ms 이하, P99 80 ms 이하 |
| 제어 명령 발행 | 30 Hz 목표, 20 Hz 미만 지속 금지 |
| 처리 queue | 깊이 1, 오래된 프레임 폐기 |
| 정상 주행 중 연속 차선 소실 | 100 ms 미만 목표 |
| 오래된 인식 결과 | 80 ms부터 감속, 150 ms에서 안전정지 후보 |

차량 설정 상한인 4.87 m/s에서 50 ms는 약 24.4 cm, 80 ms는 약 39.0 cm의 이동이다.
(실측 속도는 설정 상한에 미달하므로 실제 이동거리는 이보다 짧다. 지연 예산은 보수적으로 이 값을 쓴다.)
평균 지연만 기록하지 않고 P50/P95/P99, 최대 연속 누락, 명령 age를 rosbag과 CSV에 남긴다.

ROS 구독은 가능한 경우 sensor-data QoS와 queue depth 1을 사용한다. callback 안에서 다음
프레임을 기다리게 하지 않고, 처리 중 새 프레임이 도착하면 가장 최신 프레임만 남긴다.

## 5. 경기 모드 자원 정책

과거 개발용 센서 스택에서 삭제된 `lane_preview`가 CPU 약 60%, dashboard가 약 13%를
사용한 실측이 있었다. 현재 상시 `white_left_drive`의 자원 사용량은 Jetson 실시간
상태에서 다시 측정해야 한다.

- `dev launch`: white-left debug, dashboard, web video, rosbridge와 상세 overlay를 허용한다.
- `race launch`: 카메라, 필수 센서, 인식, FSM, 제어, 안전 watchdog, 저비용 logger만 실행한다.
- 경기 모드에서는 화면 overlay를 기본 비활성화하고 필요하면 저주기 샘플만 저장한다.
- 신호등 검출처럼 GPU가 필요한 작업은 해당 sector에서만 활성화한다.
- CPU/GPU 온도, throttling, 메모리, callback 지연을 3바퀴보다 긴 soak test에서 확인한다.

`sensors.launch.py`에는 모터를 추가하지 않는 기존 안전 계약을 유지한다. 경기용 상위 launch도
기본 `armed:=false`이며, 명시적 승인과 preflight를 통과해야 모터 chain을 포함한다.

## 6. 속도 계획

속도는 고정 상수가 아니라 다음 제한 중 가장 작은 값을 사용한다.

```text
v_cmd = min(v_sector,
            v_curvature,
            v_lane_confidence,
            v_mission,
            v_obstacle,
            v_latency)
```

- `v_sector`: 연습주행으로 얻은 구간별 상한
- `v_curvature`: 곡률과 허용 횡가속도로 계산한 상한
- `v_lane_confidence`: 차선 품질·소실시간·경로 분산에 따른 상한
- `v_mission`: 신호 판정과 분기·합류 구간 상한
- `v_obstacle`: LiDAR/초음파 안전거리 상한
- `v_latency`: 인식·명령 age가 증가할 때의 상한

급가속보다 코너 진입 전 감속과 출구 가속을 계획한다. 속도 증가는 동일 설정의 3바퀴
무벌점 반복주행을 통과한 뒤 구간별로 수행하고, 한 번에 전체 트랙 속도를 올리지 않는다.

## 7. 검증 단계와 승급 기준

1. **규정·트랙 동결**: 최신 세부 규정, 트랙 구간표, 미션 의미, 벌점을 설정으로 기록한다.
2. **카메라 동결**: 내부 보정, 장착 TF, 노출·화이트밸런스·게인을 고정하고 조명별 영상을 수집한다.
3. **오프라인 차선**: rosbag에서 중심 오차, 소실, 지연, 조향 떨림을 회귀시험한다.
4. **모터 없는 실시간**: 실차 센서만으로 30분 동안 queue backlog와 thermal throttling이 없어야 한다.
5. **저속 폐루프**: 직선부터 시작해 구간별로 확대하고 lane age watchdog과 안전정지를 검증한다.
6. **미션 단독**: 신호 시퀀스와 지름길 분기·합류를 반복해 오결정과 decision latency를 측정한다.
7. **3바퀴 내구**: 보수 속도로 반복 완주한 뒤 구간별 속도를 올린다.
8. **경기 리허설**: 경기 launch와 동일한 프로세스, 배터리, 조명, 시작 절차로 수행한다.

목표 경기 속도는 최소 10회 연속 3바퀴에서 차선 이탈·충돌·미션 오결정이 0이고,
지연 계약과 VESC fault 0을 동시에 만족한 설정 중 가장 빠른 설정으로 선택한다.

## 8. 구현 순서

1. 카메라 보정과 수동 노출 설정, rosbag 수집 도구
2. 고전 `fast_lane_perception`과 오프라인 benchmark
3. metric center path, lane confidence, timestamp/latency 계측
4. 횡제어기와 신뢰도·곡률 기반 speed scheduler
5. 트랙 sector estimator와 랩 카운터
6. 신호등 이벤트와 route-decision FSM
7. 지름길 경로·합류 제어
8. 경량 세그멘테이션 TensorRT A/B 평가
9. 개발 launch와 경기 launch 분리 및 3바퀴 자동 리포트

첫 구현 범위는 1~3이며 모터 출력은 포함하지 않는다. 카메라 보정이 유효하고 오프라인
지연 계약을 통과한 뒤에만 저속 폐루프 단계로 진행한다.
